## 3. Estrategia de importación

**Conflicto de HU-01 #3.** El UPC de las líneas 10 y 11 impide insertar ambos productos tal como llegan bajo una restricción de unicidad. Las fechas, la clasificación y el ancho también impiden proyectar algunas filas directamente. Conservar 120 registros en PostgreSQL y consultar solo los productos que cumplen las reglas preserva la fuente. La cobertura literal de 120 productos en catálogo queda parcial y debe constar en README y defensa.

1. Usar un comando local del repositorio con modo de inspección sin escrituras y modo de carga. Leer bytes, comprobar UTF-8 y cabecera y calcular SHA-256. Usar un parser CSV con soporte de comillas y saltos de línea, que capture el registro original y permita diagnosticar la longitud por fila. Tratar errores de estructura que impidan delimitar registros como fallo del archivo y reportarlo. La línea 116 sí tiene límites identificables.
2. Preparar todos los registros antes de insertar. Conservar línea de inicio y fin, texto original, ID tal como llega y campos parseados cuando se puedan identificar. Aplicar solo las normalizaciones aprobadas, con valores antes y después. Validar en orden reproducible y agrupar colisiones después de las normalizaciones. Registrar varios motivos por fila cuando corresponda. Derivar taxonomía de pares sin conflicto y validar la pertenencia con relaciones explícitas.
3. Persistir lote, filas y proyección en una transacción, con serialización de ejecuciones del comando y restricciones únicas. Identificar el lote inicial por SHA-256 y registrar versión de reglas. Una segunda corrida de la misma entrada muestra el resultado registrado. La respuesta distingue contadores de altas de esta corrida y totales de ese lote. La carga inicial inserta únicamente UPC nuevos. Si encuentra un UPC preexistente ajeno al lote, deja incidencia y conserva el catálogo. Tratar choques de unicidad bajo concurrencia con el CRUD como conflictos de fila, mediante inserción condicionada por la restricción y diagnóstico explícito. Cualquier fallo inesperado revierte la transacción y se reporta al operador. Las cuentas demo se insertan por usuario único, con hash y sin sobrescribir cuentas existentes.
4. Reportar filas leídas y conservadas, altas de categorías, subcategorías, productos y usuarios, filas vinculadas como duplicados, pendientes y advertencias. La proyección apunta a la fila de origen y los estados históricos permanecen consultables tras editar o borrar el producto. Guardar el manifiesto de reglas y, si hay correcciones aprobadas, un archivo versionado con SHA-256 de origen, línea, valor esperado, valor aprobado y motivo. Aplicar correcciones como revisión explícita con su propio resultado y control de conflictos con ediciones posteriores. La reejecución normal no restaura bajas ni sobrescribe cambios operativos.
5. Para reproducir el resultado usar el mismo CSV, reglas y migraciones sobre una BD de prueba vacía y comparar clasificación, conteos y estados. Los identificadores internos y hashes con sal pueden variar. El README documentará ejecución, resultados esperados, diferencias entre inspección y carga y cómo consultar pendientes.

**Alternativas.** Un único reporte generado por CLI reduce tablas, pero depende de conservar y distribuir archivos externos y pierde trazabilidad durable por fila. Una importación de todo o nada mantiene integridad y deja el catálogo vacío hasta recibir las correcciones. La propuesta conserva cada fila y permite probar el CRUD con los datos conciliados. Un mecanismo de correcciones completo puede esperar mientras la carga respete el manifiesto aprobado y documente el procedimiento de conciliación.

## 5. Arquitectura y esquema propuestos

Un repositorio con `api/` y `web/`, un lockfile compartido si se elige pnpm, más el Compose entregado. NestJS concentra reglas, DTO, autenticación y acceso a PostgreSQL con módulos `Auth`, `Catalog` y `Products`. El comando de importación usa la conexión de la API y las mismas restricciones de BD. Next usa App Router, una UI y un adaptador de mismo origen acotado a las rutas de este catálogo. Proponer TypeORM por su integración con Nest y migraciones explícitas. Prisma es viable si ya se domina y se incorporan los checks en SQL de migración. Mantener un solo ORM. El adaptador en Next requiere una capa HTTP pequeña y da persistencia sin exponer el JWT a JavaScript. Acceso directo con Bearer en memoria ahorra esa capa y pierde persistencia al recargar. Usar formularios y fetch con herramientas del stack, sin librerías adicionales salvo necesidades concretas como CSV, JWT, validación y hash.

| --- | --- |

La llave compuesta permite consultar subcategorías por categoría y admite códigos repetidos en categorías distintas si el negocio lo permite. |
| `products` | `id integer` de identidad PK, `upc_code varchar(12) NOT NULL UNIQUE` con check de 12 dígitos ASCII, `upc_description text NOT NULL` con check de no vacío sujeto a aprobación, `subcategory_id NOT NULL` FK restrictiva e índice para relación inversa. La categoría se obtiene por JOIN. `date_added` y `updated_date` como `timestamptz(0) NOT NULL`, con orden temporal sujeto a aprobación. `added_by` y `modified_by` como texto no vacío, con etiquetas históricas del CSV o usuario autenticado de la app. Relación de origen opcional y única a una fila importada. |
| `users` | `id integer` de identidad PK, `username text NOT NULL UNIQUE` en forma canónica consistente, `password_hash text NOT NULL`, `role text NOT NULL CHECK` en `admin` o `manager`. Select explícito del hash en login y exclusión de DTO públicos. Los actores importados no son cuentas autenticables. |
| `import_batches` | PK interna, `source_sha256` único para la carga inicial, nombre del archivo, versión de reglas y fecha de ejecución. El resumen de ejecución puede derivarse de sus filas o persistirse con el lote. |
| `import_rows` | PK interna, FK a lote con índice único `(batch_id, line_start)`, líneas de inicio y fin, ID original como texto, registro crudo, campos parseados cuando proceda, estado, diagnósticos y normalizaciones. Referencia opcional a fila canónica para duplicado exacto. Los estados históricos quedan en esta tabla cuando se borra un producto. |

Las PK y restricciones únicas aportan índices para búsquedas por ID, UPC y usuario. Mantener JOIN y orden determinista por ID en listados. La FK desde producto a subcategoría garantiza pertenencia a una sola subcategoría. Resolver `categoryCode` y `subCategoryCode` juntos al escribir para evitar desalineación. Usar migraciones versionadas con sincronización automática desactivada: primera para taxonomía, productos y usuarios, segunda para procedencia y su referencia desde producto. Ejecutarlas sobre BD limpia antes del comando local de carga. Cambios posteriores se agregan mediante migraciones nuevas.

## 6. API y pantallas propuestas

El contrato siguiente corresponde a NestJS. Las rutas de Next actúan como adaptador del navegador, mantienen el mismo origen y traducen la cookie a Bearer. La ruta de sesión de Next configura la cookie con el JWT que devuelve Nest y responde con el perfil público. Las demás rutas propagan estados y mensajes útiles sin reenviar cabeceras sensibles del backend. Para recarga, consultar la sesión mediante el adaptador y `GET /auth/me`.

| Método y ruta | Permiso | Entrada y respuesta |
| --- | --- | --- |
| `POST /auth/login` | Público | JSON `username` y `password`. 200 con `{ accessToken }`, 400 si el payload no es válido, 401 credenciales inválidas y 429 por límite de intentos. |
| `GET /auth/me` | Ambos roles | 200 con `id`, `username` y `role` públicos de la sesión validada. |
| `GET /products` | Ambos roles | 200 con todos los productos en orden estable. Campos de tabla más `id`. Admite el filtro opcional `?categoryCode=…&subCategoryCode=…` para obtener los productos de una subcategoría. Los dos parámetros se validan en conjunto. |
| `GET /products/:id` | Ambos roles | 200 con `id`, `upcCode`, `upcDescription`, `categoryCode`, `subCategoryCode`, `dateAdded`, `updatedDate`, `addedBy` y `modifiedBy`. 404 si no existe. |
| `POST /products` | Admin | JSON con `upcCode`, `upcDescription`, `categoryCode` y `subCategoryCode`. 201 con detalle guardado y `Location`. |
| `PUT /products/:id` | Admin | Los mismos campos de escritura, con validación completa de obligatorios. 200 con detalle actualizado, 404 si no existe y 409 si el UPC pertenece a otro producto. |
| `DELETE /products/:id` | Admin | Sin body. 204 si elimina y 404 si el ID no existe. |
| `GET /categories` | Ambos roles | 200 con lista de `code`. |
| `GET /categories/:categoryCode/subcategories` | Ambos roles | 200 con `code` y `categoryCode` de cada subcategoría. 404 para categoría inexistente. Los productos correspondientes se consultan por su relación. |
| `POST /api/auth/logout` en Next | Navegador | Elimina la cookie incluso si expiró la sesión y responde 204. La UI regresa al login. |

Los identificadores de URL deben ser enteros positivos, con 400 para formato inválido y 404 para un ID válido inexistente. Las escrituras devuelven 400 para campos faltantes, tipos incorrectos o clasificación inexistente o incompatible, 409 por UPC ocupado y 401/403 según identidad y rol. Formato de error uniforme con `statusCode`, `code` y `message`, `fieldErrors` cuando corresponda y `requestId` para correlación. Las fechas se serializan como `YYYY-MM-DDTHH:mm:ssZ`. La app genera fechas UTC de precisión de segundos en servidor. Guardar UPC siempre como cadena y usar input de texto con teclado numérico para preservar ceros.

| Pantalla | Flujo |
| --- | --- |
| `/login` | Usuario y contraseña, error genérico, estado de envío y redirección a catálogo. Si el token venció, volver al login. |
| `/products` | Tabla con las seis columnas, acceso al detalle y cerrar sesión. Admin ve crear, editar y eliminar. Manejar carga, error, vacío y reintento. |
| `/products/[id]` | Detalle completo con autores y fechas UTC, regreso al listado y 404 visible. Acciones solo para admin. |
| `/products/new` y `/products/[id]/edit` | Formulario compartido, errores por campo, validación previa del UPC con listado, selectores de valores existentes y pareja válida. Confirmar tras aceptación de API y refrescar lista. Reutilizar detalle para precargar edición. |
| Confirmación de borrado | Diálogo con descripción o UPC del producto, cancelar y confirmar. Deshabilitar repetición mientras se procesa. Refrescar lista al éxito y mantener mensaje claro ante error. |
